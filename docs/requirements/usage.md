# Requirements: Usage & Efficiency

Part of little-workshop's requirements register; conventions and the other parts are in [../requirements.md](../requirements.md). Sections keep the order and headings of the round that added them.

## Claude usage, collection: the Usage & Efficiency pillar (M19, 2026-10-04)

| ID | Description | Status |
| --- | --- | --- |
| REQ-000000324 | **The intake stores each API request and tool call once.** When Claude Code posts an OpenTelemetry log export to the intake, the Usage & Efficiency pillar shall store each `api_request` event as one request row (its request id, session, time, model, the four token counts, the estimated cost and the query source) and each `tool_result` event as one tool-call row with a normalized signature, shall count a request or tool call it already holds only once whichever source sent it, shall never store prompt or response text, and shall answer every post with success so that a session never sees an error from it. | draft |
| REQ-000000325 | **Hooks and the statusline tell where a session ran and how full the plan is.** When a Claude Code session posts a hook or its statusline data to the intake, the Usage & Efficiency pillar shall record from a session-start, session-end or compaction hook the session's working directory, transcript path and end reason, shall keep the event, and shall record the plan's 5-hour and 7-day usage percentages the statusline reports. | draft |
| REQ-000000326 | **The transcript backfill covers what telemetry missed.** When the `usage.ingest_transcripts` Job runs or a session-end hook names a transcript, the Usage & Efficiency pillar shall read the transcript files under the Claude projects directory with a parser that skips lines it cannot read, shall store their requests and tool calls under the same request and tool-use ids telemetry uses so that nothing is counted twice, shall add the 1-hour share of a cache write that only the transcript knows, and shall not read again a file that has not changed. | draft |
| REQ-000000327 | **Each session is attributed to a project and an origin.** The Usage & Efficiency pillar shall attribute every session to the first of: the project tag little-workshop put on a run it started; the registered checkout that contains the session's working directory, the longest one winning and a git worktree traced to its repository; the registered project whose repository telemetry names; the workspace folder that holds several checkouts; and otherwise `unattributed`; and shall record the origin as `job`, `query` or `interactive`. | draft |
| REQ-000000328 | **Requests are compiled into per-day rollups, metrics and weeks.** The Usage & Efficiency pillar shall compile the stored requests into one rollup per day, project, origin and model that holds the token sums, the weighted tokens per token type priced from a per-model table the owner can override, the context tokens and the share of them in requests above 200,000 tokens; shall keep a day's rollup when the requests behind it are pruned, with a retention never under 35 days; shall return for one week starting on Monday the per-day series, the totals with cache hit ratio, average context per request, long-context share and median startup context, the per-project totals, the heaviest sessions, the previous week, the next week and the average of the four weeks before where those have data, and the weekly weighted tokens spent on little-workshop against every other project; and shall purge a removed project's rows. | draft |
| REQ-000000329 | **The user profile is shown first and applied only when asked.** When the `usage.configure_claude` Job runs, the Usage & Efficiency pillar shall report what the Claude user profile (the telemetry environment, the session hooks, the statusline and a transcript retention of at least 90 days) would change in the user's Claude settings file, and only when the Job's `apply` parameter is true shall write it, after copying the file beside itself, keeping every entry the owner made, leaving a statusline of the owner's own and a longer retention as they are, and never enabling the logging of prompt or response text. | draft |
| REQ-000000330 | **usage.doctor reports what collection depends on.** When the `usage.doctor` Job runs, the Usage & Efficiency pillar shall check without changing anything that the intake is listening, that the user profile is in place, what `claude doctor` reports, that each language server of the code-intelligence plugins is on the path, and that data arrived in the last seven days, shall give each failed check a hint that says how to fix it, and shall keep the report for the Dashboard. | draft |
| REQ-000000332 | **The pillar is optional and its intake is reached through a loopback port.** The Usage & Efficiency pillar shall be an optional pillar enabled by default that binds only its Unix socket, and when it starts it shall choose the first free loopback port from 4318 upward once and keep it in its configuration, and shall start a systemd user socket unit that listens on that port on 127.0.0.1 and passes each connection to its socket, reporting rather than failing when the proxy cannot be started. | draft |

## Claude usage, findings (M20, 2026-10-04)

| ID | Description | Status |
| --- | --- | --- |
| REQ-000000335 | **Detectors turn the stored usage into findings.** When the `usage.analyze` Job runs, the Usage & Efficiency pillar shall measure every project over the last 14 days with twelve deterministic detectors that use no Claude (D1 long-context share and sessions above 500,000 tokens; D2 startup context grown over its 30-day median; D3 cache rebuilds that neither a session start nor a compaction explains; D4 one-request runs writing a 1-hour cache; D5 one-request runs spread over many directories; D6 requests that only poll or wait; D7 commands whose results average above 20 kB; D8 files read in five or more sessions; D9 routine calls made on an Opus or Fable session; D10 raw calls repeated where a route replaces them; D11 MCP servers connected and never used; D12 job runs on days above the plan-pressure threshold), each against a threshold the pillar's configuration can change, shall open one finding per flagged detector and project with its evidence, an estimated weekly saving and the recommended action, shall refresh rather than duplicate a finding it already holds, shall leave a dismissed finding dismissed, shall resolve an open finding that is no longer flagged, and shall list findings ranked by estimated saving. | draft |
| REQ-000000336 | **An applied optimization is measured before and after.** When an optimization is started for a finding, the Usage & Efficiency pillar shall record an experiment with the finding's metric over the seven days before; and when the `usage.measure_experiment` Job names that experiment or the `usage.analyze` Job runs at least 14 days after it began, the pillar shall measure the same metric over the last seven days, shall resolve the finding when the metric fell, and shall reopen the finding when it did not. | draft |
| REQ-000000337 | **Optimize Claude usage is a fixed task built from the chosen findings.** When the `usage.optimize` Job runs for a project with chosen findings, the Usage & Efficiency pillar shall create one `agent.run_task` Job on that project's queue with intent `improvement`, manual review and a fixed description that embeds a digest of those findings written by the pillar itself and the same for the same findings, shall mark the findings accepted, shall refuse findings that are not open for that project, and shall change nothing when Orchestration cannot be reached; and the Dashboard's job catalog shall offer it as Optimize Claude usage for every project with the project's open findings as its choices, beside Apply common Claude configuration and Configure Claude telemetry for little-workshop only. | draft |

## Claude usage, automation: mining and workshop triggers (M21, 2026-10-04)

| ID | Description | Status |
| --- | --- | --- |
| REQ-000000341 | **Repeated tool-call episodes are mined into scored candidates.** When the `usage.mine_automation` Job runs, the Usage & Efficiency pillar shall group the tool calls of the last 14 days into episodes of one prompt each, shall take as a candidate every normalized signature and every run of two or three consecutive signatures that recurs in at least three sessions or at least ten times and is not exploration only, shall give each candidate five checks (argument derivability, output stability, checkability, no content creation, bounded branching), the class deterministic when all pass, hybrid when it creates no content and at least three pass and heuristic otherwise, the weighted tokens its occurrences cost per week, a proposed form and example episodes without file contents, shall rank the candidates by weekly cost, and shall use no Claude and implement nothing. | draft |
| REQ-000000342 | **A candidate is made a task, dismissed or scheduled by a person.** The Usage & Efficiency pillar shall keep each mined candidate with its state and shall give it a recommended schedule derived from how often its episodes occurred (daily or weekly on the weekdays they occurred most) at night with the candidates' runs one after another; when the `usage.automate` Job names an open candidate the pillar shall create one fixed `agent.run_task` improvement task on little-workshop that carries the candidate's evidence and shall mark the candidate accepted; a candidate shall be dismissed, reopened or marked done only on request; and for a candidate with a named replacement the pillar shall record the tokens avoided as the replacement's stored runs times the median cost of the episodes it replaced. | draft |

## Claude usage, token-aware operation (M22, 2026-10-04)

| ID | Description | Status |
| --- | --- | --- |
| REQ-000000349 | **Unattended Claude jobs wait while the plan's 5-hour window is nearly full.** While the Usage & Efficiency pillar reports the plan's 5-hour usage at or above the owner's limit (80 percent unless configured) from a reading no older than five hours, the Orchestration pillar shall leave queued every Job that uses Claude and was created by a schedule or a trigger, shall dispatch as usual every Job a person started and every Job that runs only code, shall ask for the reading at most once a minute and never while holding its dispatch lock, shall hold nothing when that pillar is switched off, unreachable or without a recent reading, and shall pump its queue on every scheduler tick so that a held Job starts once the window has room again. | draft |
| REQ-000000350 | **Tokens are reported per finished task, finished branch and requirement done.** The Usage & Efficiency pillar shall note on every tick each succeeded branch finish Orchestration holds once and each registered project's count of done requirements for the day, and shall return per week and project the weighted tokens beside the agent task runs that finished with their cost per task, the branches finished with the tokens per branch and the requirements that turned to done with the tokens per requirement, giving no value where a week had no such outcome or no reading; and the summary, the MCP tool, the CLI and the Dashboard's Claude usage page shall show the chosen week's outcomes. | draft |

## Automation candidates valued by their net saving (2026-10-04)

| ID | Description | Status |
| --- | --- | --- |
| REQ-000000356 | **A candidate is valued by what automating it would really save.** When the `usage.mine_automation` Job values a candidate, the Usage & Efficiency pillar shall estimate from the stored sessions, before anything is built, the weighted tokens per week automating it would save: when Claude calls the replacement, the turns beyond one that its occurrences took (calls made in the same request counting as one turn, each turn at the weighted cost of its request) plus the output beyond a short answer that later requests of the session re-read, less the new tool's own cost in every session's starting context; and, only for a pillar action that is neither a read nor a decision a trigger may not make, when a trigger or a schedule runs it, all of its turns and output; shall rank candidates by the better of the two, leave out a candidate worth less than $0.10 a week, show both estimates on the Dashboard and in the improvement task, and count tokens avoided as the replacement's runs times what one run saves when Claude calls it. | draft |

## Automation estimates replayed against their sessions (2026-10-04)

| ID | Description | Status |
| --- | --- | --- |
| REQ-000000357 | **The estimate replays each occurrence and says how well its constants fit.** When the `usage.mine_automation` Job runs, the Usage & Efficiency pillar shall value each occurrence of a candidate by replaying it against the thread it happened in (the session's main conversation or one subagent's), counting what its own content added to the conversation as re-read by every later request of that thread until the next compaction or clear at that request's own price per context token, shall fit the call overhead and the bytes per token on every stored turn and test that fit on the newest 30% of turns it was not fitted on, shall fall back to the constants measured on 2026-10-04 while fewer than 200 turns are stored, shall give each estimate a low figure that assumes the replacement makes Claude check on it once more, shall keep and serve what the estimates rest on for the Dashboard, and shall read each subagent's transcript as a thread of its session without changing the session's own directory, transcript or version. | draft |

## Usage & Efficiency: plugin proposals (2026-10-07)

| ID | Description | Status |
| --- | --- | --- |
| REQ-000000416 | **Repeated requests that are mostly deterministic are proposed as Claude Code plugins.** When automation mining runs, the Usage & Efficiency pillar shall take as one request each state-changing call of a prompt that is not housekeeping, together with the calls code could make right before it and the reads and waits right after it, stopping at a judgment call (reading or writing files, free text, an inline or scratch script, a here-document other than a commit message) unless it lies between two runs of the same step, group the requests of the last 14 days by the family of that call (its variants, such as a feature, improvement or hotfix finish by MCP or by lws, being one family), and propose one Claude Code plugin for each group seen in at least 3 sessions or 10 times, of at least 2 calls on median, in which Claude made a judgment call in at most 25% of the requests, covering the steps in at least 25% of its requests and listing the rarer ones apart. | draft |
| REQ-000000417 | **A plugin proposal states exactly how much Claude it uses, today and with the plugin.** The Usage & Efficiency pillar shall give each plugin proposal its frequency (occurrences per week and daily, weekly or occasional), its calls, turns and tokens per occurrence, the weighted cost per week of its requests today and of the Claude turns left with the plugin (only the judgment calls at its fallback points, as they cost when they happened, plus the plugin's command in every session's context), and each fallback point with the step it follows, how often and how often after that step failed, the tools Claude used there and its cost; it shall rank the proposals by the net saving per week and not list one worth less than $0.10 a week. | draft |
| REQ-000000418 | **A plugin proposal is for one project or for all projects, installed from a local marketplace.** Superseded: a proposal is drafted as a skill instead of shown with an install command (REQ-000000507). | superseded by REQ-000000507 |
| REQ-000000419 | **Plugin proposals are listed and decided.** The Usage & Efficiency pillar shall store the plugin proposals each mining run finds, keep the decision a person made on one (accepted, dismissed, done) and drop the open ones mining no longer finds, and shall list them by state through GET /v1/plugin_proposals, the MCP tool workshop_usage_plugin_proposals and lws usage plugin-proposals, while the plugins installed are listed by Claude Code's own claude plugin list. | draft |
