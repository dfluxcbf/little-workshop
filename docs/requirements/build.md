# Requirements: Build & Packages

Part of little-workshop's requirements register; conventions and the other parts are in [../requirements.md](../requirements.md). Sections keep the order and headings of the round that added them.

## M11 — Build & Packages

| ID | Requirement | Status |
|---|---|---|
| REQ-000000105 | Fork-safety-gated PR testing: `build.run` accepts `from_fork: bool` (default `false`), persisted on the `BuildRun`. `build.publish_pypi`/`build.publish_vsix` require a real `build_run_id` and are refused — `"fork-safety gate: a fork-triggered build run cannot publish"` — whenever that run's `from_fork` is `true` or its `status` isn't `succeeded`; a fabricated flag on the publish call itself can't bypass this, since the gate is checked against the pillar's own stored record of the run, not caller-supplied claims. | done |
| REQ-000000106 | `little-pypi` absorbed for the package-hosting half, always-on rather than session-lifetime: package *metadata* (`kind`, `name`, `normalized_name`, `version`, `filename`, `source_build_run_id`) lives in this pillar's own database — a deliberate modernization of `little-pypi`'s pure-filesystem/no-DB model, consistent with every other pillar's own "database, not a shared file" convention — while the artifact *blobs* stay on disk (`Paths.package_blob_path`), matching `little-pypi`'s own "blobs on disk" shape unchanged. | done |
| REQ-000000107 | A real PEP 503 Simple Repository API (`build/pep503.py`): `normalize_name` collapses runs of `-`/`_`/`.` to a single `-` and lowercases, per spec; `GET /simple/` lists every published project as `<a href="{name}/">`; `GET /simple/{name}/` (name normalized on the way in) 404s for an unpublished project or else lists every one of its files as `<a href="../../packages/{filename}">`; `GET /packages/{filename}` serves the real blob bytes — computed live from the database on every request, never regenerated-to-disk index files the way `little-pypi`'s own filesystem-only model needed. | done |
| REQ-000000108 | `.vsix` (VS Code extension) hosting is its own namespace, deliberately never part of the PEP 503 index (matching `little-pypi`'s own real behavior: `.vsix` files share physical storage with wheels but were never `simple/`-indexed): `GET /vsix/{name}` lists every published version, `GET /vsix/{name}/{version}` downloads the real blob. | done |
| REQ-000000109 | `build.delete_package` removes both the database row and the on-disk blob together — never one without the other, so a deleted package can never appear in a listing with no file behind it, or the reverse. | done |

## M16 follow-up — parity survey and rejecting compatibility shims (2026-09-17)

| ID | Requirement | Status |
|---|---|---|
| REQ-000000165 | **`little-pypi`'s dev-convenience gaps, closed.** Four new `lws build` subcommands — `print-pip-config`, `write-pip-config`, `pip`, `print-vsix-urls` — matching `little-pypi`'s own `print-pip-config`/`write-pip-config`/`pip`/`print-vsix-urls`. All are pure CLI-side additions (`src/cli/main.py` only — no `src/build/` change): the first three never call the pillar's Pillar Interface at all (a pip.conf text template, and a real `subprocess.run` shell-out to `python -m pip install --extra-index-url ... --trusted-host ...`); the fourth is a plain `GET /v1/packages?kind=vsix` read, formatted as `{base}/vsix/{name}/{version}` URLs. All four assume a real HTTP reverse proxy already sits in front of Build & Packages' own Unix-socket-only Pillar Interface at the given `--host`/`--port` — the same deployment-time-concern split `docs/pillars/dashboard.md`'s browser-exposure section already documents for the identical reason (`docs/architecture.md`'s PI transport: "never a network port"); nothing here builds that proxy. | done |
