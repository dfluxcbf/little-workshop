# Documentation standard

Sources: `docs/governance_policy.md` ("The `docs/{design,architecture,milestones}.md` habit — kept in
full"), `docs/open_questions.md`, `docs/requirements.md` conventions, `docs/pillars/README.md`, the
agent prompt `src/agent/templates/prompts/docs.md`.

> The super-repo's `docs/policies/documentation_policy.md` and `docs/README.md` are referenced by
> several project docs but do not exist. This file is the working replacement.

## Required documents

Every project has, under `docs/`:

| File | Holds | Must contain |
|---|---|---|
| `design.md` | Concepts and decisions: *what* and *why* | Purpose, goals, non-goals, core concepts, data/behaviour flows; a revision note when a round changes direction |
| `architecture.md` | How it is implemented | Components, interfaces, configuration and data locations, data model, feature mapping, technical decisions with reasons, dependencies, build, additional folders |
| `milestones.md` | The work sequence | An overview table (ID, objective, depends on, status) then one section per milestone: objective, dependencies, status. Requirements are listed by id, not restated |
| `requirements.md` or the Requirements pillar | The requirements | See [requirements_standard.md](requirements_standard.md) |
| `open_questions.md` | The single tracker of unresolved questions | See below |
| `requirements_policy.md`, `version_policy.md` | The project's own policy statement | Either point at the governing policy or state the rule in full, plus a "Project-specific notes" section |

Larger projects add `docs/pillars/<name>.md` (one per component: description, purpose and goal,
responsibilities, interfacing) with an index in `docs/pillars/README.md`, and topic documents such
as `first_run.md` or `ui_design.md`. Every document is reachable from `design.md`,
`architecture.md` or the project `README.md`.

A project `README.md` carries a one-paragraph purpose, first-time setup, the canonical commands,
and a pointer to `docs/`. A `.claude/AGENTS.md` holds only what a Claude session must know before touching
the project (tooling, hard "never" rules, test and deploy commands) and links to `docs/` for
everything else. It is `AGENTS.md`, not `CLAUDE.md` or `AGENT.md`, and a project has no `CLAUDE.md`:
Claude Code reads `AGENTS.md` only where there is none, and does not read `AGENT.md` at all (hand edit
2026-10-01, the rule moved to `.claude/AGENTS.md` for every project).

## Writing rules

1. **Do not duplicate content across files; link to the authoritative one.** Documents must be
   consistent with each other and with the code.
2. **Docs are the record, corrected as understanding improves.** Correct a wrong statement in
   place and date the change; do not leave a stale statement beside a new one.
3. **A rule change is deliberate, documented at the point of change, and dated** (governance).
4. **Milestone documents state objective and dependencies, not requirements text.** A milestone's
   requirements are drafted as its first real task.
5. **Describe what exists, not what is hoped.** Mark planned work as planned, with a status.
6. **Enough detail to implement without asking.** A "later" milestone row must be specific enough
   that someone could build it without further clarification.
7. **No code changes from a documentation task**, unless a doc change strictly requires a tiny
   accompanying fix, which the summary says.

## Open questions (`open_questions.md`)

- Stable ids `OQ-NNN`, assigned in raised order, never reused, even when dropped.
- Each item has: where it comes from; first designed; design goal; pillars affected; what is
  actually being asked; why it matters; possible interpretations; a **Your answer** field.
- Answered items move to **Resolved** with a date and a pointer to where the reasoning is
  written up; every affected document is updated.
- Any session that surfaces a new question or gap adds it before it ends, instead of leaving a
  "left open" footnote elsewhere.
- Projects that use another scheme (Ethereal Lands: `#q-01` / `#o-01` anchors in
  `docs/design/16-open-items.md`) keep it; see the project folder.

## Review and certified sections

Documents can be reviewed in the Dashboard's doc review. A reviewer's comment applies **only** to
its own highlighted section. A **certified** section is settled: do not change it unless a comment
makes it unavoidable, then change as little as possible, preserve its meaning, facts, structure and
wording, and say so in the comment's note.

## Generated and protected content

Respect markers such as `<!-- name -->` ... `<!-- /name -->`: those blocks are regenerated by a
tool and must not be hand-edited. Directories a task declares untouchable stay untouched.
